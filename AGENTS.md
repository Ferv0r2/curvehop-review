# Agent instructions — Curvehop public review edition

This repository is an executable review snapshot of Curvehop with fictional data. Read README.md, docs/architecture.md, and SOURCE_MANIFEST.json before changing it.

AGENTS.md is the single source of agent instructions here. Codex reads this file and Claude Code reads it through CLAUDE.md (`@AGENTS.md`). Do not copy these rules into tool-specific files. Repeatable procedures live in `.agents/skills/<name>/SKILL.md` and are listed at the end.

## Scope

- Preserve the distinction between byte-identical source files, declared adaptations, and generated fixtures. Do not claim changed files are identical to the source snapshot.
- Keep company, job, evidence, and logo fixtures fictional. Do not add collected content, credentials, production settings, research workers, or publication automation.
- Keep request preferences outside shared public-data caches. Preserve revision invalidation, error recovery, and concurrent-request isolation.
- JEV evaluates stored excerpts. Its confidence threshold is not accuracy, and its decisions have no publication authority.
- Use the installed Next.js documentation when changing framework behavior. Keep UI changes consistent with the existing styles and components.
- Local review does not authorize deployment, paid API calls, or changes to external services.

## How changes land

- This repository is generated. The maintainer's export toolkit writes every file together with its hash in SOURCE_MANIFEST.json, and `pnpm verify:source` fails on any hand edit to a listed file. Do not edit the manifest to make it pass.
- The maintainer exports a change onto a branch named `<type>/<short-topic>`. Use one of `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, and keep one concern per branch.
- `main` is protected by a repository ruleset. Direct pushes, force pushes, and deletion are blocked. Every change needs a pull request that passes the `verify` check and is squash-merged.
- Commit messages and PR titles follow `type(scope): summary` in the imperative mood. Describe the actual change. Never backdate commits or reconstruct history.
- Fill in `.github/pull_request_template.md` with what changed, why, which checks ran, and what remains unverified.
- Do not merge with a failing, cancelled, or skipped check. If CI cannot start, report it instead of bypassing the rule.
- Outside contributors: open an issue. A pull request that edits listed files cannot pass `verify` by design.
- In a checkout you may build, run checks, and preview changes. You can also regenerate diagrams locally. None of these land a change.

## Definition of done

- Run the checks that match the change (`verify-change` skill). Build before HTTP tests. Report exactly what ran and any remaining limitations.

## Documentation and diagrams

- Architecture diagrams are generated by `docs/architecture/build.mjs` and captured by `docs/architecture/capture.mjs` (`architecture-diagram` skill). Do not edit the generated HTML or PNGs by hand.
- Separate the operating system (private pipeline, deployment) from what this repository runs. Code links in the diagram's decision list carry an `ops:` mark for operations-only paths. When SOURCE_MANIFEST.json is present, the generator fails if a mark disagrees with this checkout. Components drawn inside the private zones are operations-only by placement.

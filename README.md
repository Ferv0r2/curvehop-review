# Curvehop

공고의 기술 목록을 다 읽어도 남는 질문이 있습니다.

> 이 회사는 무엇으로 돈을 벌고, 나는 어떤 팀에서 일하게 될까?

공고만 봐서는 회사가 무엇을 만들고 어떻게 일하는지 알기 어렵습니다. [커브홉](https://curvehop.net)은 공고에서 출발해 회사 설명과 근거가 달린 읽을거리까지 이어 읽으며 지원할 회사를 알아보는 서비스입니다. 설명마다 출처를 연결하고 확인된 사실과 아직 답이 부족한 항목을 나눠 보여 줍니다.

이 저장소는 운영 소스의 웹 앱을 가상 데이터로 돌려 볼 수 있게 만든 공개판입니다. API 키 없이 로컬에서 실행됩니다. 아래 설계 결정 세 가지가 막으려는 실패는 테스트로 직접 재현해 볼 수 있습니다. 실제 회사 조사와 운영 자동화는 이 저장소에서 실행하지 않습니다.

처음 보신다면 [5분 검토 동선](docs/review-guide.md)부터 따라가 보세요. 전체 구조는 [아키텍처](docs/architecture.md)에, 판단 근거는 [설계 결정 3가지](docs/design-decisions.md)에 정리했습니다.

## 구조

![운영 서비스의 전체 구조: 비공개 배치가 수집과 조사, 검토를 미리 끝내고, 발행 관문을 통과한 자료만 main을 거쳐 Cloudflare Workers에 배포된다. 페이지 요청은 배포된 자료만 읽고 끝난다.](docs/architecture/overview.png)

운영 서비스는 오래 걸리는 일과 요청에 응답하는 일을 나눴습니다. 미니PC가 정해진 시각에 수집과 조사, 검토를 미리 끝냅니다. 그중 발행 관문을 통과한 결과만 자료 갱신 PR로 main 브랜치에 머지해 배포합니다. 페이지 요청은 배포된 자료만 읽으므로 처리하는 동안 모델이나 수집기, Git을 호출하지 않습니다.

그림의 파란 점선 영역이 이 저장소에 담긴 Next.js 앱입니다. 운영에서는 Cloudflare Workers에서, 로컬에서는 Node에서 돌아갑니다. ①부터 ⑤까지 번호마다 무엇을 판단했고 무엇을 감수했는지는 [아키텍처 문서](docs/architecture.md#운영-전체-구조)에 적었습니다. 저장소를 받은 뒤 `docs/architecture/architecture.html`을 브라우저로 열고 판단 항목에 마우스를 올리면 그림에서 해당 위치가 강조됩니다.

## 실행

Node.js 24를 권장하며 최소 22가 필요합니다. pnpm은 10.28.2를 씁니다.

```sh
pnpm install --frozen-lockfile
pnpm dev
```

[http://127.0.0.1:3100](http://127.0.0.1:3100)을 열고 공고를 하나 고른 뒤 회사와 읽을거리로 넘어가 보세요. 가상 회사 3곳, 공고 15개, 읽을거리 12편이 들어 있습니다. 데이터 기준일은 2026-10-22이며 실제 채용 정보가 아닙니다. API 키나 `.env` 파일은 필요 없습니다.

## 설계 결정

| 막으려는 문제 | 선택과 감수한 비용 | 코드와 테스트 |
| --- | --- | --- |
| 다른 사람의 직무 조건이 내 목록에 섞인다 | 공개 자료만 공유하고 조건은 요청마다 조합한다. 파일 상태를 확인하는 비용은 남는다. | [자료 캐시](lib/published-data.ts), [요청 분리 HTTP 테스트](tests/ssr-reads-http.test.mjs) |
| 자료가 갱신됐는데 느린 이전 요청이 옛 내용을 돌려준다 | 읽기 전후로 자료 버전을 확인한다. 버전이 계속 바뀌면 세 번 시도한 뒤 오류를 낸다. | [자료 버전 캐시](lib/revision-cache.ts), [경쟁 상태 테스트](tests/revision-cache.test.ts) |
| 근거보다 강한 설명이 모델 평가를 통과한다 | 근거와 범위, 인과를 따로 판정하고 불확실하면 보류한다. 평가에는 발행 권한을 주지 않는다. | [JEV 판정 계약](lib/jev-shadow.ts), [경계값 테스트](tests/jev-shadow.test.ts) |

표의 핵심 모듈은 기준 소스와 바이트까지 같습니다. 결정마다 이유와 검증 범위는 [설계 결정 문서](docs/design-decisions.md)에 이어서 적었습니다.

앱은 Next.js App Router, React, TypeScript로 만들었습니다. 질문별 답변은 [질문 정의](lib/research-questions.ts)에서 시작해 [근거와 범위 평가](lib/question-assessment.ts)를 거쳐 [화면 표시](lib/question-view.ts)로 이어집니다. 자료가 저장돼 있다는 것만으로 질문에 답했다고 보지 않습니다.

## 검증

```sh
pnpm typecheck
pnpm test
pnpm test:sensitivity
pnpm build
pnpm test:http
pnpm verify:source
```

`test:http`는 운영용 빌드로 검사하므로 `pnpm build`를 먼저 실행하세요. 어디까지 검증하는지, 코드를 어떤 순서로 읽으면 되는지는 [검토 가이드](docs/review-guide.md)에 정리했습니다.

## 공개 범위와 출처

기준 소스는 운영 저장소의 `d0e55193900a71f1f4d0fefdf714e20de849792a` 커밋입니다. 웹 런타임과 관련 계약을 가져왔고 데이터, 실행 설정, 일부 테스트는 공개 검토용으로 구성했습니다.

[SOURCE_MANIFEST.json](SOURCE_MANIFEST.json)에는 파일마다 원본과 바이트가 같은지(`exact`), 공개판에서 바꿨는지(`adapter`), 새로 만들었는지(`generated`)를 해시와 함께 기록했습니다. `pnpm verify:source`는 비공개 저장소 없이 공개 파일의 무결성을 확인합니다. 다만 원본 저장소를 볼 수 없는 사람이 원본의 진위까지 확인할 수 있는 검사는 아닙니다.

들어 있는 것은 웹 화면, 탐색과 필터, 북마크, 자료 읽기와 검증, 질문 모델, JEV 계약과 모의 전송 테스트입니다. 웹이 의존하는 수집 관련 유틸리티도 함께 들어 있습니다.

빠진 것은 미니PC에서 도는 운영 작업 코드와 조사, 발행을 실행하는 진입점, 조사 프롬프트, 실제 수집 원문과 실행 기록, 원본 저장소의 전체 Git 이력입니다. 코드와 실행 범위의 경계는 [아키텍처 문서](docs/architecture.md)에서 설명합니다.

# 코드로 확인하는 설계 결정 3가지

결정마다 사용자에게 보이는 문제, 선택한 경계, 그것을 확인하는 테스트 순서로 적었습니다. 1번과 2번은 [전체 구조](architecture.md#운영-전체-구조)의 ④, 3번은 ②에 해당하고, 셋 다 이 저장소의 테스트로 직접 확인할 수 있습니다.

## 1. 공개 자료는 공유하고, 사용자 조건은 요청에서 조합한다

두 구직자가 동시에 프론트엔드와 백엔드 공고를 보면 자료는 같아도 목록은 달라야 합니다. 요청마다 모든 파일을 새로 읽으면 같은 일을 반복하게 되고, 사람별 결과를 공유 캐시에 넣으면 다른 요청으로 조건이 섞일 수 있습니다.

[`published-data.ts`](../lib/published-data.ts)는 바뀌지 않는 공개 자료를 자료 버전별로 재사용합니다. [`render-data.ts`](../lib/render-data.ts)는 렌더 한 번 안의 중복 읽기를 묶고, [`preference-store.ts`](../lib/preference-store.ts)는 요청 쿠키를 따로 읽습니다. 공개 자료와 사용자 조건은 [`repository.ts`](../lib/repository.ts)에서 합칩니다.

정해진 유효 시간 동안 이전 자료를 계속 내주는 대신, 호출할 때마다 파일 상태를 확인합니다. 그래서 캐시가 채워진 뒤의 요청에도 `stat` 호출 비용은 남습니다. 회사 조사 자료의 버전에는 관계 파일과 UTC 날짜도 들어가므로, 관계를 정정하거나 날짜가 바뀌면 읽기 결과에 반영됩니다.

[`ssr-reads-http.test.mjs`](../tests/ssr-reads-http.test.mjs)에서 볼 동작은 세 가지입니다. 동시에 들어온 프론트엔드와 백엔드 요청의 조건이 섞이지 않는지, 빈 필터를 명시하면 저장된 선호를 덮어쓰는지, 파일을 바꾼 뒤 응답이 달라지는지입니다. React `cache`가 요청 단위로 나뉘는지는 운영용 빌드로 띄운 실제 서버에서 확인해야 합니다. 단위 테스트에서 함수만 호출한 결과로 대신하지 않습니다.

## 2. 읽기 순서가 뒤집혀도 새 자료를 지킨다

공고 제목이 바뀐 뒤에 느린 이전 요청이 옛 제목을 돌려주면 안 됩니다. 버전 A의 파일 읽기가 늦어지는 사이에 B가 먼저 끝날 수 있습니다. A가 끝나는 시점에 캐시를 다시 채우거나 현재 캐시를 무조건 지우면 더 최신인 B를 잃습니다.

[`revision-cache.ts`](../lib/revision-cache.ts)는 읽기 전과 후, 결과를 돌려주기 직전에 자료 버전을 확인합니다. 실패한 항목을 지울 때는 `entry === current`를 검사해서 다른 요청이 넣은 항목은 남깁니다. 자료가 계속 바뀌면 최대 3번 시도한 뒤 오류를 냅니다.

[`revision-cache.test.ts`](../tests/revision-cache.test.ts)의 경쟁 상태 테스트는 A를 멈춰 두고 B를 끝낸 다음 A를 풀어 줍니다. 두 요청이 모두 B를 돌려주는지, 파일을 더 읽지 않는지 확인합니다. 크기가 같고 수정 시각까지 되돌린 변경, 파일 삭제와 복구, 실패한 읽기 작업을 다시 쓰지 않는지도 같은 파일에서 검사합니다.

캐시가 채워진 뒤 서버 렌더의 파일 읽기가 0번이라는 결과는 그대로 믿을 수 없습니다. 계측이 동작하지 않아도 0이 나오기 때문입니다. 그래서 [`ssr-measure.mjs`](../tests/helpers/ssr-measure.mjs)는 시작할 때 실제 파일 `open`이 관측되는지부터 확인합니다(양성 대조). [`instrumentation.test.mjs`](../tests/instrumentation.test.mjs)는 계측 결과가 비어 있으면 이 단계에서 실패하는지 검사합니다. 그다음 대표 경로의 요청에서 파일 읽기 호출을 모두 셉니다. 이것은 파일 읽기가 다시 늘지 않았는지 보는 검사이고, 요청 지연이나 운영 p95를 잰 것은 아닙니다.

## 3. 모델의 판단과 발행 권한을 나눈다

국민연금 가입자가 5명 줄었다는 기록만 보고 직원 5명이 퇴사했다고 쓰면 구직자를 잘못 이끌 수 있습니다. 저장한 발췌를 평가할 때는 숫자가 맞는지뿐 아니라 범위와 인과를 넘겨짚지 않았는지도 봐야 합니다.

[`jev-shadow.ts`](../lib/jev-shadow.ts)는 외부 평가 모델 JEV가 근거와 범위, 인과를 하나씩 따로 판정하도록 규칙을 정합니다. 코드에서는 각각 `support`, `scope`, `causality`입니다. 모델 ID, 응답 형태, 확률의 합, 고른 값과 가장 높은 확률이 일치하는지, 신뢰도 값의 관계를 검사합니다. 세 항목이 모두 충분한 신뢰도로 `supported`일 때만 `pass`이고, 하나라도 충분한 신뢰도로 `unsupported`이면 `flag`, 나머지는 `abstain`(보류)입니다. 형식이 틀린 응답은 판정으로 치지 않습니다.

기준값 `0.75`는 `choice.confidence`에 적용합니다. 선택 확률이 0.75라거나 정확도가 75%라는 뜻이 아닙니다. 반올림된 응답이 기준을 넘은 것처럼 보이지 않도록 확률에서 신뢰도를 다시 계산해 함께 확인합니다. [`jev-shadow.test.ts`](../tests/jev-shadow.test.ts)는 0.75 경계, 0.749 보류, 불확실한 응답, 잘못된 응답, 반올림을 검사합니다.

판정을 모은 결과에는 `publicationAuthority: false`와 `modelAccuracyClaim: 'not_established'`가 들어갑니다. `pass`도 조사가 끝났다거나 사실임이 보증됐다거나 발행해도 된다는 뜻이 아닙니다. 공개판은 미리 만든 입력과 응답으로 이 규칙을 검사할 뿐, 실제 모델 응답의 품질은 측정하지 않습니다. 자세한 규칙은 [JEV 판정 규칙](jev-shadow-evaluation.md)에 있습니다.

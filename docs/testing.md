# 테스트를 어디까지 두는가

지원자가 서로 다른 조건으로 탐색해도 결과가 섞이지 않을 것, 바뀐 자료를 읽을 것, 검증 실패를 성공으로 해석하지 않을 것. 이 세 가지가 먼저입니다. 테스트 개수나 줄 커버리지 목표는 두지 않습니다.

## 계층별 책임

| 계층 | 잡아내는 실패 | 이 계층만으로 주장하지 않는 것 |
| --- | --- | --- |
| 순수 함수와 판정 규칙 | 경력 0년과 미기재의 구분, 명시적인 전체 직무 선택, 직군 단어 충돌, JEV 경계값과 위조된 응답 | 실제 페이지의 요청 경계, 모델의 의미 판단 정확도 |
| 순서를 제어한 비동기 실행 | A 읽기를 멈춘 사이 B가 끝나는 순서, 실패한 읽기 작업에서의 회복 | 운영 환경에서 생길 수 있는 모든 실행 순서 |
| 가짜 전송 | 여러 입력에서의 호출 상한, 첫 오류 뒤 중단, 저장에 실패하면 요청 차단, 다시 평가할 때 입력이 같은지 확인 | 실제 유료 API의 품질과 가용성 |
| 운영용 빌드의 HTTP 응답 | 동시 사용자 조건 분리, 파일 변경 뒤 본문과 메타데이터 갱신, 오류 뒤 실제 내용 복구 | 클릭, 키보드, 스크롤, 모든 화면의 시각 품질 |
| 가상 데이터 검증 | 등록 가능한 회사 3곳, 검색 조합, 비교할 수 있거나 없거나 빠진 인원 정보, 근거가 바뀌면 이어 읽기 연결 해제 | 글자 수로 판단하는 콘텐츠 품질 |

겹쳐 보여도 맡은 일이 다른 검사는 남겼습니다. `revision-cache.test.ts`는 자료 버전을 직접 넣어 경쟁 순서를 정확히 제어하고, `published-data.test.ts`는 실제 읽기 코드가 UTC 날짜를 자료 버전에 넣는지 확인합니다. 직무 우선순위 단위 검사는 규칙 자체를, HTTP 검사는 그 규칙이 요청별 쿠키와 실제 결과에 적용되는지를 봅니다.

예제 데이터 생성 결과를 같은 함수의 결과와 한 번 더 비교하던 검사는 뺐습니다. 다시 생성했는지는 저장된 스냅샷과 비교해 확인합니다. 안내 글의 최소 글자 수도 품질 기준으로 쓰지 않습니다. 이어 읽기 연결은 비어 있지 않은지, 자기 자신이나 중복을 가리키지 않는지, 실제 대상이 있고 근거가 바뀌면 풀리는지를 봅니다.

## 테스트가 결함을 잡는지 재현하기

```sh
pnpm test:sensitivity
```

[`check-test-sensitivity.mjs`](../scripts/check-test-sensitivity.mjs)는 임시 복사본에서 정상 테스트가 먼저 통과하는지 확인한 뒤, 아래 결함을 하나씩 넣어 봅니다. 작업 중인 체크아웃은 건드리지 않고 API 키나 외부 API도 필요 없습니다. 결함을 하나라도 못 잡으면 명령이 실패합니다. 문법 오류나 시간 초과, 로드 실패는 결함을 잡은 것으로 세지 않습니다.

| 넣어 보는 결함 | 확인하는 것 |
| --- | --- |
| 오래된 요청이 현재 캐시를 무조건 지움 | 자료 버전의 경쟁 상태 |
| 갱신 재시도 상한을 3번에서 1번으로 줄임 | 재시도 횟수 제한 |
| 조사 자료 버전의 UTC 날짜를 고정하거나 한국 날짜로 바꿈 | 실제 읽기 코드와 자정 경계 |
| `role=`를 지정하지 않은 것처럼 처리 | 명시적인 전체 직무 선택 |
| JEV의 세 항목 중 하나만 통과해도 승인 | 판정 집계 |
| 신뢰도 0.75 경계를 빼 버림 | 기준값 |
| 요약 결과에 발행 권한을 줌 | 평가와 발행의 분리 |
| 한 번에 보내는 호출 상한을 무시 | 전송 수와 선택 순서 |
| 첫 전송 오류 뒤에도 다음 호출을 계속 | 오류 뒤 중단 |
| 다시 평가할 때 사례 해시 검사를 생략 | 입력이 같은지 확인 |
| 요청 전에 실행 기록 저장을 생략 | 저장과 요청의 순서 |
| 캐시가 채워진 뒤의 읽기 횟수 비교를 제거 | 계측 검증이 실제로 동작하는지 |

2026-10-22 점검에서는 처음 고른 결함 12개 중 6개가 기존 테스트를 그대로 통과했습니다. 테스트를 보강한 뒤 12개를 모두 잡았고, UTC 대신 한국 날짜를 쓰는 결함을 더해 지금은 13개가 모두 단언 실패로 잡히는지 검사합니다. 이것은 위 목록의 결함을 재현한 결과일 뿐, 프로그램 전체의 변이 점수나 결함이 없다는 보증이 아닙니다. 결함을 넣을 기준 문자열이 사라지면 실험도 실패하므로, 리팩터링할 때는 각 결함의 의미가 유지되도록 함께 고쳐야 합니다.

서버 렌더 계측은 세 가지를 함께 확인합니다. 시작할 때 실제 파일 읽기가 관측되는지(양성 대조), 캐시가 채워진 뒤 요청의 파일 읽기가 0번인지, 자료를 강제로 바꾼 뒤 실제 파일 읽기가 다시 관측되는지입니다. 계측 결과가 비어 있거나 비교 단계가 빠져도 통과해 버리는 경우는 별도의 음성 대조로 막습니다. 이것은 파일 읽기가 다시 늘지 않았는지 보는 검사이고 지연 시간을 재는 벤치마크가 아닙니다.

## 일부러 남겨 둔 범위

운영 수집과 발행 작업, 실제 모델의 의미 판단 평가, 브라우저의 모든 탐색 동작은 이 공개판의 자동 테스트 범위가 아닙니다. 브라우저 QA는 따로 했지만, CI가 북마크나 뒤로 가기, 접근성을 모두 검증한다고 주장하지 않습니다. 새 테스트는 재현할 사용자 실패나 규칙 위반이 있을 때 추가하고, 같은 계층에서 같은 입력과 실패를 확인하는 검사는 하나로 합칩니다.
